# Item matching

The free deployment profile uses Cloudflare Workers AI with `@cf/google/gemma-4-26b-a4b-it` and no paid fallback. Keep the Cloudflare account on Workers Free. Review the [provider selection and data terms](FREE_MATCHING_PROVIDERS.md) before sending reports.

Both providers receive report fields and normalized item photos, with structured output, no tools and `store:false`. Account records, profile photos, session tokens and claim evidence stay inside Reunite. Report text and photos can themselves contain personal details. Users should attach only the item and redact unrelated people/contact information.

## What runs

- A PostgreSQL trigger queues opposite LOST/FOUND reports from different users when both are OPEN. A reconciliation query repairs concurrent-insert gaps and discovers legacy reports in batches of 200. Categories prioritize the queue; they do not exclude a pair. Location/date differences are evidence, not undocumented eligibility rules.
- `report_matches` is the only added table: ten physical tables in total. It stores one durable job/result per report pair, both content revisions, leases, attempts and cumulative cost reservations. No ORM, Redis or second HTTP backend is added.
- The standalone Node startup hook runs one sequential worker per process. Vercel runs one job per authenticated scheduler request. PostgreSQL leases and `SKIP LOCKED` coordinate concurrent workers. Each job has up to three attempts. Terminal errors remain inspectable by an operator in `error_code`. Logs omit raw provider responses.
- Report edits invalidate old leases/results and requeue current content. Completion checks both revisions and OPEN status. Same-user, closed/resolved and stale matches are excluded. Match notifications commit atomically with a successful result and are emitted at most once per pair; later edits can invalidate a previously announced suggestion.
- The dashboard has no persistent matching panel. The bell polls notifications every ten seconds while visible and shows an in-app alert for fresh suggestions. The alert opens the comparison and return confirmation in a dialog over the current page. Queue length, provider latency, retries and budget can delay suggestions.
- Results never change report/claim status or decide ownership. There is no fabricated similarity percentage. A `possible_match` needs two distinct agreeing identity attributes, including model/marking/contents/damage, and no conflicts. Otherwise the display gate abstains. This conservative heuristic still needs measured evaluation; it is not a proven accuracy threshold.

## Configuration and costs

### Cloudflare Workers Free on Vercel

1. Apply migration `0010`. Use a Cloudflare Workers Free account and a token scoped to that account's Workers AI inference. Store `CLOUDFLARE_WORKERS_AI_TOKEN` as a Sensitive Production variable in Vercel and set `CLOUDFLARE_ACCOUNT_ID` to the corresponding account ID.
2. Set `MATCHING_PROVIDER=cloudflare`, `MATCHING_BUDGET_USD=0`, and `MATCHING_FREE_DAILY_LIMIT` between 1 and 10. The database reserves attempts centrally using UTC dates, including retries. A provider throttle pauses queue claims according to `Retry-After`, or for 15 minutes if the provider omits a valid delay. The Cloudflare account's own free allocation also applies.
3. Generate a 32-byte random lowercase hex secret. Set it as Sensitive Production `MATCHING_RUNNER_SECRET` in Vercel and in Supabase Vault as `reunite_matching_runner_secret`. Assign read access to the release operator only. Deploy with `MATCHING_ENABLED=true`, then run [schedule-matching.sql](../infra/supabase/schedule-matching.sql) as the Supabase release operator. The scheduler invokes the protected `POST /api/internal/matching/run` once per minute and logs only execution status. Keep the Data API disabled.
4. Verify a real inference and both return confirmations using disposable reports without personal data. Check `cron.job_run_details`, the API's matching status and the Cloudflare Free usage dashboard. To stop scheduling, run `SELECT cron.unschedule('reunite-match-items');` as the release operator. A redeploy with `MATCHING_ENABLED=false` stops inference.

### Existing OpenAI configuration

Leave `MATCHING_ENABLED=false` and `MATCHING_BUDGET_USD=0` until credentials, budget and privacy review are ready. Put `OPENAI_API_KEY` in the server's private environment/secret manager, never in chat, Git or `NEXT_PUBLIC_*`. Host scripts use root `.env`; Next dev uses `apps/web/.env.local`; Compose passes runtime server variables. Restart the server after changing them. `bun run env:check` checks these values without printing secrets. An explicitly enabled worker with missing key or insufficient budget fails startup validation.

`MATCHING_BUDGET_USD` is a **lifetime cumulative reservation cap for this database**, not a daily/monthly limit or a provider invoice total. Every network attempt reserves USD 0.10 in a transaction protected by an advisory lock. Concurrent instances see a fresh sum after that lock. Failed calls, timeouts and stale results retain the reservation because upstream charging may have occurred. A successful response records an estimate from actual token usage separately. Reservations are deliberately not refunded; budget can stop well before actual billed spend reaches the cap. Do not reset/delete cost rows to resume processing; raise the approved cumulative cap deliberately. The FK restricts report deletion while cost/job history exists; no delete API is introduced. Retention/deletion accounting needs a future explicit policy.

Pricing checked November 16, 2026: USD 0.75 / 1M uncached input tokens and USD 4.50 / 1M output tokens. Calls limit non-image UTF-8 input/schema/prompt to 100,000 bytes, at most two normalized 1024px photos, and 2,048 output tokens. The USD 0.10 reservation conservatively covers 120,000 input + 2,048 output at those rates. Unknown model snapshots, excessive usage, malformed/refused/incomplete outputs and redirects fail closed. There is no configurable upstream URL or server fetch of arbitrary image URLs. Recheck pricing before enabling; model/rate changes require a code review of the bound. Set a separate provider project hard spend limit, especially if other applications share its key. Currency conversion, tax, other keys and future provider price changes are outside this application ledger.

Pair enumeration is exhaustive across open opposite-type reports and grows with LOST × FOUND. The free daily allowance can leave suggestions queued overnight. Review queue size, time-to-result, EXPLAIN plans and evaluated candidate retrieval before large deployment.

## Item images

`PUT /api/v1/item-reports/:id/image` accepts the owning user's raw JPEG/PNG/WebP body, at most 4 MiB. The server verifies the decoded format, rejects animations, limits input pixels/time, auto-orients, strips EXIF/GPS and resizes inside 1024×1024 without cropping. Normalized WebP is bounded to 1 MiB and stored on `item_reports.image_data`; no ephemeral upload folder is used. GET requires a signed-in viewer, matching report visibility. Mutation endpoints require session ownership and same-origin. GET `/image/access` is owner-only metadata for the detail dialog's attach/replace/delete controls. DELETE clears the bytes/reference and invalidates matching. PATCH of an external `image` reference also clears stale stored bytes. Legacy/external image URLs remain links; the AI never retrieves them. Upload a local item image to include its pixels in comparison.

## API

`GET /api/v1/matches[?before=<matchId>]` requires a session and returns 20 current suggested pairs plus `nextCursor`, `pendingCount`, `failedCount`, `serviceStatus` (`disabled`, `active`, `budget_exhausted`) and `refreshAfterSeconds:10`. Each pair has `matchId`, own/candidate report IDs and titles, assessment and completion time. Counts cover materialized jobs only; the reconciler may still be discovering pairs. No global usage/key/account identifiers are exposed. Responses are no-store. Unknown/duplicate/invalid query parameters are rejected.

Image routes: authenticated `GET /api/v1/item-reports/:id/image`; owner-only `GET /api/v1/item-reports/:id/image/access`, `PUT /.../image`, `DELETE /.../image`. Missing/non-owned mutations return a non-disclosing 404. `MATCH_SUGGESTED` with a pair ID opens its dialog. The direct route `/matches/:id` opens the same dialog over the signed-in user's list. Older notifications without a pair ID open `/matches`.

## Confirming a return

`GET /api/v1/matches/:id` is private to the two reporters. It returns the relevant report details, the caller's role, both revision strings, and the confirmation timestamps. `PUT /api/v1/matches/:id` accepts `{ lostRevision, foundRevision }` over same-origin authenticated requests. The server derives the role from ownership. After physically exchanging the item, the owner confirms receipt and the finder confirms handoff. The first confirmation leaves both reports open and alerts the other participant. The second resolves both reports and alerts both participants in one transaction. Retrying either confirmation preserves the recorded timestamp and does not emit another alert.

Changing an open report invalidates pending confirmations. A stale submission is rejected so both reporters can review the updated pair. Confirming a return does not alter claim decisions. Migration `0009` adds columns to the existing tables.

## Verification and release limits

Run `bun run matching:status` for safe aggregate queue counts, enabled/key-present booleans, lifetime reserved USD, estimated completed costs and remaining reserved calls. It does not print keys or item/account data. Estimated completed cost excludes unpublishable stale results and unknown timeout/refusal charges; reservations are deliberately never refunded. Reconcile the actual invoice in the provider project, not from that estimate. Increasing the configured lifetime ceiling is an explicit operator decision; do not delete accounting rows to reset spend. Failed terminal jobs require investigating `error_code` and an operator-controlled retry after the underlying issue is fixed; existing reservations must remain intact.

Unit tests exercise the real request/response contract with a **stub HTTP transport**, including inline images, strict results, refusals, oversized payloads and invalid model output. PostgreSQL integration tests exercise real migrations, atomic queue writes/rollback, concurrent budget claims, expired leases, retry caps, stale content, authorization, image decoding and notification idempotency. These tests establish application behavior; **they do not establish the model's live API compatibility or matching accuracy**.

Live provider verification needs a private key from the selected account. Use fictional reports for the initial smoke check. Measuring accuracy also requires independently labelled same/different item pairs, including similar-looking negatives, Thai/English descriptions, omitted/incorrect fields, zero/one/two photos and photo lighting/angle variations. Split development and held-out sets by physical item to prevent leakage. Review labels manually and record dataset/model/prompt versions.

`bun run matching:evaluate <private-labelled-results.json>` calculates precision, recall, confusion counts and abstentions from saved provider assessments after the same display gate. Input: a non-empty array of `{ "id": "unique-pair-id", "sameItem": true, "assessment": <validated model result> }`. A true pair with abstention counts as a missed suggestion. Undefined precision/recall is `null`, never 100%. This command makes no network requests and incurs no API charge. Do not publish real photos, contact details or labels in Git. No target precision/recall or sample size has been approved, so production accuracy certification remains open.
